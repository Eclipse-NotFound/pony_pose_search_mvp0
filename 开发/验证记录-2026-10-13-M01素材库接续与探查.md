# M01 素材库接续与自动处理探查

2026-10-13。用户报告当前素材库没有素材，希望调查 M01，并为图片、MP4、FLA 保留适合各自特点的自动处理。沿用原有成熟模块界面；本轮未实施新的选帧算法或工程渲染器。

## 空库原因与修复范围

正常 `run_m10.bat` 经 `scripts/launch.ps1` 打开项目默认 `data/pose_library_v2`。只读盘点得到 386 条观测、337 份图片资产，但 `sources/catalog.sqlite3` 内素材文件、位置、根目录、任务全部为 0。此前 `experiments/module_merge_cde_20261013/staging_library` 已迁移 1,243 个素材，而多格式测试使用 `experiments/format_e2e_20261013/library-final`；它们都不是日常默认库。

原因确认：旧姿态数据已经进入默认库，素材编目与候选／角色框的接续只在测试副本完成，日常库缺少这一步。没有把测试副本整体替换到默认库。

修复采用现有 `workflow.migration.migrate`，在接续前用 `workflow.inventory.create_copy` 保存独立副本及 SQLite 一致性备份。迁移只读取项目现有 CSV／JSON／PNG，追加版本化记录；源文件改变、已有后续人工修订或裁剪像素不一致时保留冲突，不强行覆盖。

备份：`experiments/m01_processing_20261013/backup-before-default-reconnect/`。此副本保留外部图片引用，不是脱离项目的便携包。没有修改 `D:/活/AE/素材/泄露素材`，也没有把整个原素材目录批量导入。

本轮接续范围为旧候选表与框表引用的 1,243 张 PNG；项目 `frames/` 总计 2,647 张，并非本轮把所有文件自动选为候选。精确位置指已保存的 PNG，旧 CSV 时间保留为旧证据，不冒充原视频精确帧。

迁移任务已完成：384 份点位接续、1,285 条旧候选表条目、437 个角色框；连同框表对应集合形成 1,722 个候选。173 条旧裁剪逐像素吻合后追加素材位置绑定。没有缺失的 CSV 引用图片。具体记录在 `migration-job.json` 及默认库 `workflow/migrations/migration_f416bd1a5e7942eebbd41bc9c0a8b383.json`。

保留的问题：`obs_legacy_b8180aa63928b45658c83c470bdb681b` 缺少原图尺寸，不建立可训练点位；`s01e15_t000026_f000_twilight_unicorn_001` 和 `s01e15_t000190_f000_twilight_unicorn_001` 的裁剪像素与框不吻合，保留旧来源。没有把这些冲突标成成功。

最终验证完成，证据为同目录 `restoration-result.json`、`annotation-preservation.json`、`daily-ui-check.json`：

- 386 条观测和 337 份图片资产保留，旧文件清单与全部旧修订指纹未变；逐条比较确认全部 386 条的方向值及部位数据未改写。
- 库结构与修订父链校验通过。图片检查仍报告 1 份既有纯色图、1 份既有缺图，不宣称这两项已修复。
- 从 `ControlCenter(root, PROJECT)` 的正常默认入口打开原生 Tk 控件，M01 显示“1 页 · 共 1243 件”，首屏 50 行，空库提示隐藏；读取一个已有画面并加载一条已绑定的旧标注成功，错误列表为空，未编辑标签。

## M01 代码与能力核对

- `scripts/m01/extract_frames.py`：已转为共同流程 CLI 入口。
- `scripts/common/workflow/dataset.py`：`queue_frames`／`sample_frames` 目前是明确起止帧与步长，图片和视频可用，每任务最多 10,000 帧。
- `scripts/common/source_catalog/store.py`：登记、版本、位置、队列。`media.py` 负责实际解码和结构读取。
- `scripts/m10/native_workbench.py`：批量取帧窗口默认起止都是 1、步长 24。导入文件只登记与读取元信息，不自动生成候选；FLA 没有可用画面渲染。
- 单帧读取每次启动 FFmpeg；大规模自动处理需要增加顺序解码路径，同时保留原有精确跳帧能力。
- 本次迁移产生 21 个扫描任务（分批登记到两个相同根目录）和 1,243 个读取任务；迁移本身又同步取得所需图片元信息。最终全部正常完成，但存在重复扫描／读取成本，新处理计划应合并同根扫描并复用同版本已完成的读取结果。

## 本轮只读探针

在四段已知短 MP4 上读取实际时间戳与全部低分辨率灰度帧，计算完全重复及全图差异；同时读取两个现代 FLA 主文档。使用 FFmpeg／ffprobe 9.0.1，探针为 `experiments/m01_processing_20261013/probe_sampling.py`，机器结果为 `sampling-probe.json`。

四段视频逐帧数量为 126／459／107／96，按整秒取最近源帧仅得到 6／20／5／4 张。灰度图完全相同相邻帧均为 0。每段分析含元信息与帧索引读取约 0.48—0.81 秒，不能外推长视频。四份内容指纹与 2026-10-11 相同；本轮处理前后原文件指纹也相同。

`MLP925_020.fla` 主场景 106 帧、6 图层、1,139 个库元件；主时间轴存储关键帧起点集合只有 `[0]`。对应 MP4 107 帧。因此仅取主关键帧会忽视嵌套动画，同名预览不能直接赋予工程帧号。暮光模板主场景 8 帧、2 fps、105 元件，进一步说明模板不能统一按剧集视频抽样。

没有渲染两个 FLA，没有新增标注或训练，没有测量动作召回率。灰度变化只是选帧研究线索，既不能证明模型精度提高，也不能当作不同姿势的标签。

## 规划与接续

详见 [M01 多格式自动处理方案](../设计/方案卡-2026-10-13-M01多格式自动处理.md)。建议先补图片／视频自动生成候选及相似画面折叠，再接原生 FLA 场景渲染、预览关联，最后扩展角色模板与完整角色输出。结果仍交原有 M02—M09，不建立另一套标注／检索界面。

当前 Animate MCP 不在本会话可调用工具中，邻近项目 README 也明确尚未安装／接入日常客户端。官方 PNG 序列能力说明只支持方案可行性，不构成此次本机渲染成功证据。
