# M01 多格式素材自动处理

2026-10-13。本文保留探查时的实施建议；后续已接入角色 FLA 的场景／库元件导出，并验证现代暮光、旧 OLE 穗龙，详见[角色 FLA 实施记录](../开发/验证记录-2026-10-13-角色FLA接入.md)。视频自动挑选、相似折叠及场景嵌套实例隔离仍未实施。用户已明确：保留自动处理；沿用成熟的 M02—M09 筛选、标注和搜索界面，不再建立另一套工作台。

## 要解决的问题

M01 应把文件变成可筛选、可定位的画面。图片是一张画面，MP4 是连续画面，FLA 则可能是一段场景动画，也可能是一册角色角度和零件模板，不能统一理解为“每隔一秒截一张”。

推荐主流程：**登记原文件 → 自动判断可用处理方式 → 生成候选画面并折叠相似项 → 原有 M02 筛选 → M03 角色框 → M04 样本 → 原有标注与搜索**。自动生成的候选默认待判断，不因自动处理就变成合格训练数据。

## 已查到的事实

1. 默认 `data/pose_library_v2` 有 386 条姿态观测，但素材文件、位置、根目录和任务均为 0。旧资料接续及多格式测试之前都在独立副本进行，未接到日常默认库。此次修复与新选帧算法是两件事。
2. `scripts/m01/extract_frames.py` 已是共用流程入口。实际逻辑位于 `scripts/common/workflow/dataset.py`、`scripts/common/source_catalog/`，界面入口在 `scripts/m10/native_workbench.py`。
3. 当前导入只扫描、识别格式并生成元信息／缩略图，不自动排队候选画面。批量画面窗口默认为起止第 1 帧、步长 24 帧；它并非按每个文件的实际时间取一秒。图片／视频可以建立画面位置，FLA／XFL 暂不支持渲染。
4. 当前视频批量取帧会逐个位置启动 FFmpeg，逐次校验文件；大量连续候选不适合继续沿用这条单帧读取路径。单帧精确读取可保留给用户跳转。
5. 2026-10-11 的全量盘点：6,791 个 FLA（3,112 个现代 ZIP/XML、3,679 个旧 OLE）、1,138 个 MP4、391 个 MOV、715 个 SWF、6,451 个 JPG。JPG 中 6,449 个只有 96×54 或 192×108，主要适合作为预览。此处引用既有盘点，本轮未重新遍历整个素材目录。

本轮只读复查四段 MP4，文件 SHA256 均与 10 月 11 日一致。每段一次低分辨率逐帧分析及元信息读取约 0.48—0.81 秒；只代表这些短片，不代表长视频性能。

| 视频 | 实际帧数 | 每整秒取最近源帧所得数量 |
|---|---:|---:|
| MLP925_012 | 126 | 6 |
| MLP925_016 | 459 | 20 |
| MLP925_020 | 107 | 5 |
| MLP922_067Z | 96 | 4 |

在 160×90 灰度图上，四段均无完全相同的相邻帧。这说明“只去掉完全相同的帧”在这批压缩视频中几乎不起作用，不能据此认定每帧姿势都不同。MLP925_020 最大的画面变化发生在最后近黑的一帧，说明“取变化最大帧”也不等于取最佳姿势。

FLA 复查更关键：`MLP925_020.fla` 主场景 106 帧，主时间轴所有图层的存储关键帧起点只有 0，库里却有 1,139 个元件；不能仅凭主时间轴关键帧推断整段画面静止。对应 MP4 有 107 帧，暂不能把其帧号直接套到 FLA。`stk_c01_twilight_sparkle.fla` 主场景只有 8 帧、帧率为 2，另有 105 个库元件；这些帧应视作可能的模板条目，不能按普通剧集节奏抽样。

## 不同素材如何处理

| 素材 | 推荐默认处理 | 必须保留的信息／边界 |
|---|---|---|
| PNG、JPG、静态 WebP | 一图一个画面，自动进入待筛候选；尺寸、透明度、近似重复只作提示 | 原文件版本、图像方向与尺寸；小缩略图不自动混入合格训练集 |
| 短 MP4、MOV 镜头 | 逐帧低分辨率分析；选有代表性的画面，相似画面折叠，可展开整段补选 | 原视频流、原始解码帧序号、实际时间戳；不把处理后的顺序号当原帧号 |
| 长视频 | 先识别镜头分段，再在段内保留基础覆盖与变化附近画面；后台分段接续 | 即使没有明显切镜，也必须有段内覆盖；不能只留镜头开头 |
| 场景 FLA／XFL | 读取场景和嵌套时间轴信息，在工程副本上渲染连续画面，再应用视频式筛选 | 场景、实例路径、局部时间轴与源帧映射；补间的中间姿势也要进入分析 |
| 角色／绑定模板 FLA | 枚举完整角色视角、姿态条目与相关元件时间轴；每个条目至少保留代表画面 | 不是把所有眼睛、嘴型、蹄子零件当完整角色；未能自动确认时提供条目预览供选 |
| 背景、道具、布局 FLA | 登记、预览、分类；只有发现可用角色画面才进入姿态候选 | “有文件但暂无角色候选”是正常状态，应说明原因 |
| 旧 OLE FLA | 登记后由 Animate 在副本上打开并导出；不可当 ZIP/XML 解析 | 缺少原生渲染能力时显示“等待工程渲染”，不生成空姿态 |
| SWF、动画 WebP／GIF 等 | 明确各自解码能力，后续接专用适配器；当前不足时保留文件级编目 | 动画 WebP 当前只有文件级能力；GIF 当前不属于已支持的静态图输入 |

FLA 路线使用 Animate 的真实画面输出作为判断依据。Adobe 提供从舞台或库元件导出逐帧 PNG 的能力；舞台实例的缩放等变换会反映在输出中。[Adobe 官方说明](https://helpx.adobe.com/animate/desktop/exporting-and-publishing/exporting.html)

当前本机会话没有可调用的 Animate MCP，邻近 `animate-mcp` 项目也尚未安装到 Animate 并接入日常客户端。现有接口的场景预览、存储关键帧检查并不等于已经完成“任意角色元件、任意工程”的渲染支持。此部分是实施依赖，不能宣称本轮已跑通。

## 自动选帧：推荐的默认方案

考虑过三种方向：固定间隔最简单，但容易漏掉短动作；全部画面直接交用户筛选最完整，但重复很多；推荐的是**机器逐帧看一遍，先向人展示代表画面，允许展开全部位置**。

具体分两层，避免让姿态模型决定所有素材是否有机会被看见：

1. **不依赖角色模型的基础处理。** 保留首尾有效区域、镜头边界附近及最低时间覆盖；结合图像差异找变化段。黑场、模糊、近似重复生成提示或折叠组，默认不永久删除。
2. **可选的角色与姿态辅助处理。** 已有可靠检测器时，比较角色局部而非整张画面，减少镜头移动、背景和特效干扰。方向、视角和相对位置变化共同用于挑选；检测失败和新物种仍回到第一层，低置信度留给人检查。

基础切镜可以利用 FFmpeg 的 `scdet` 或 `select` 相关能力，但它们检测的是画面变化，不能提供姿势变化的保证。[FFmpeg 官方文档](https://ffmpeg.org/ffmpeg-filters.html#scdet)

默认提供“自动挑选”；同处保留“逐帧查看”和“按间隔取帧”作为可选方式。间隔模式明确区分“每 N 秒”和“每 N 帧”。前者按真实时间戳找源帧，不能假定 24／25／30 fps。具体相似度阈值、候选预算、最大覆盖间隔先用验证集校准，不把这次小探针的数字直接定成产品默认。

**两类去重分开处理。** 为减少人反复看，可以折叠相似画面；为训练去重，可以限制相邻近似样本数量；为了搜索定位，所有出现位置仍必须保留。同一姿势在不同源文件或帧出现时，用户仍能找到每个位置。

## FLA 如何体现工程价值

对有场景成片的工程，同时保留“整个场景”和“可单独取得的角色”两种画面。用户已决定：工程图层中实际存在完整角色时，按完整角色处理；不能因为成片被桌子挡住就降低它的姿态完整性。前提是已经取得并核验隔离后的角色画面，不能仅凭图层名字猜测。

对角色模板，先识别完整角色实例、角度／变体条目，再深入必要的元件。主场景帧、元件局部帧、实例的循环／单帧设置、父级缩放和镜像都影响实际画面。只抓 XML 中的部件变换不足以替代视觉标注；之前已经看到图层名称与所引用部件不一致的案例。

同名 MP4 可先独立进入视频流程，同时登记为“可能对应的预览”。关联确认后才记录映射：可为一对一、分段偏移、删增帧或变速映射。没核验时搜索结果可以找到同名 FLA 文件，但不能显示“已精确定位其第 N 帧”。

## 继续共用现有数据结构

保留现有 `files → versions → positions → candidates → regions → observations`，不另建第二份素材或标注库。新增的内容主要描述“这次为什么选这些画面”，而不是复制姿态记录。

| 建议增加的记录 | 主要字段／作用 |
|---|---|
| 处理计划 | 文件及版本、范围、处理方式、参数、算法版本、渲染能力与目标候选集；先给出可执行范围和限制 |
| 处理运行 | 计划指纹、解码器／渲染器版本、任务状态、分段进度、失败原因、缓存清单；复用现有任务队列 |
| 选帧证据 | `position_id`、选中原因、质量提示、变化分数、所用模型版本；新运行追加证据，不覆盖人工决定 |
| 相似画面组 | 代表位置、全部成员的轻量源位置、算法及阈值；可以展开，不把成员物理删掉 |
| 工程渲染定位 | 工程版本、场景／元件时间轴标识、实例路径、源帧序号、局部帧映射、舞台或隔离角色、坐标变换、渲染环境 |
| 关联映射 | 预览文件与工程的两个版本、映射类型、对应位置、核验依据与状态；同名只作为线索 |

内部帧号从 0 开始，界面从 1 开始。图片的精确位置仅指这张图片本身；旧 PNG 文件名或旧 CSV 时间不得自动升级成精确原视频帧。全部位置保持与其源版本绑定，重新扫描改版素材时建立新位置。

批量解码应顺序读取一次，分段写分析结果；只为代表候选生成高分辨率缓存，其余位置需要时读取。分析阶段的成员定位只保存源版本、视频流、帧序号和时间戳；成为候选或被用户展开时才通过位置服务取得图像。现有 `create_position` 会同时写 PNG，不能为了建立分组就对所有帧逐次调用它。长视频的索引和进度必须分块保存。

重复运行通过“源版本＋计划指纹”避免重复；重算沿用候选集与位置身份，追加选择证据，人工排除、选入和标注不被重算覆盖。工程适配器需扩展位置服务，提交渲染图像及可验证的工程定位；单独导入导出的 PNG 只能得到图片级位置，不能自动成为 FLA 精确位置。补齐执行中取消、失败重试和磁盘预算，不只依赖现有“暂停整个队列”。

本次旧资料接续还暴露重复工作：分批登记在两个相同根目录产生了 21 次扫描任务，已经由迁移同步读取的图片随后又执行元信息读取。新自动处理应合并同根待扫描任务，并在来源版本和读取配置一致时复用完成结果。训练数据分组也要保留同镜头、同模板以及已核验的跨格式关联，不能把同一动作的不同导出文件当成互相独立的训练与验证样本。

## M10 中如何出现

保留当前模块导航与已有标注、检索页。M01 仍是文件列表＋预览＋少量操作：

- 添加文件／文件夹后，先显示已登记数量与可自动处理的类型，允许直接开始“自动生成候选”。
- 选中文件显示“已登记／分析中／候选已生成／等待工程渲染／失败待重试”，并显示候选数和进入 M02 的入口。
- 处理选项集中在一个窗口；按类型给出推荐值，不让用户每次填写起止帧和 24 帧步长。
- M02 沿用原来的选入／排除操作，增加相似组数量与展开入口。M05／M07／M08 的操作方式保持原样。
- 明确当前资料库路径。“没有登记文件”“筛选条件没有匹配”“已有文件但还没生成候选”使用不同提示。旧记录存在而素材目录为空时，提供带备份和结果摘要的旧资料接续入口；不把打开空库等同于自动全盘导入。

## 建议实施顺序与验收

1. **接续日常库与入口诊断。** 本轮先执行既有迁移并备份，核对原标注修订和原文件未被覆盖。后续在 M01 补库路径、分层空状态及接续摘要。
2. **图片和视频自动处理。** 先实现处理计划、顺序解码、候选生成与折叠、进入 M02；保留手动范围模式。复用现有精确视频位置和后台队列。
3. **FLA 场景与预览关联。** 接通可验证的原生渲染器后，先支持少量现代场景工程，再验证 OLE 工程。用 PNG 序列及映射清单接入同一候选流程；同名 MP4 先独立使用。
4. **角色模板与完整角色输出。** 验证嵌套时间轴、角度变体、镜像、补间、遮罩和被挡角色的隔离输出，再扩展到多角色、多物种，避免先全量导入零件。

最小验证集建议包含：上述四段短片、一个较长且多镜头的视频、一个变帧率测试视频、普通大图和小缩略图、一个现代场景 FLA、一个 OLE FLA、暮光模板以及含遮罩／嵌套元件的工程。真实文件只读，处理在独立库或工程副本中验证。

比较固定间隔、完整逐帧候选、自动折叠方案时，分别记录：人工确认的不同姿势覆盖、需要看的候选数量、误折叠数量、时间／缓存占用、源位置准确性。覆盖和识别准确率不能用“选了更多张”代替。先由代理形成对照并让用户少量抽查；本轮没有这套动作全集，故尚不能声称自动选帧提高了模型精度。

实施门槛：源帧定位、断点接续、重复运行不覆盖人工决定、混合目录部分失败继续、工程无渲染能力时原因清楚。长片速度与模板枚举覆盖仍须实测。相似阈值和分组可以重新计算，反转成本较低；丢弃原位置或混同工程／视频帧会破坏检索可信度，因此不采用。
